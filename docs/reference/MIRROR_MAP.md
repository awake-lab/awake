# Mirror Map: Awake UI DSL vs. Jetpack Compose

Awake's `ui-core` DSL (`UiModifier`, `row()`/`column()`/`box()`, `animateFloat*`,
`graphicsLayer`) is deliberately shaped to *feel* like Jetpack Compose -- chainable
modifiers, slot-lambda scopes, `weight()`, `animateFloatAsState`-style helpers -- so that
a Compose developer's muscle memory transfers. It is not a Compose-compiler-plugin
runtime: there is no recomposition, no snapshot state, no constraint negotiation.
Following `kotlin-multiplatform-api-mimicry`'s method, this doc catalogs each mimicked
primitive against Compose's real current public shape and calls out three states:
**Faithful** (same ergonomics, same behavior a Compose developer would expect),
**Diverges** (looks Compose-shaped but behaves differently -- the dangerous category,
since it passes a glance-review and then causes a layout/render bug later), and
**Not implemented** (a real gap, not necessarily a deviation). Every row below is backed
by a direct read of the current source under
`awake/engine/ui/ui-core/src/commonMain/kotlin/io/github/ronjunevaldoz/awake/ui/`, not
memory of Compose or of this codebase from an earlier session.

Use this doc before reaching for a Compose idiom in Awake code: check whether the row
below says "Faithful" (safe to assume Compose semantics) or "Diverges" (read the
deviation detail first).

## `UiModifier`

Source: `modifier/UiModifier.kt`, `LayoutModifiers.kt`, `StyleModifiers.kt`,
`ScrollModifiers.kt`, `StateModifiers.kt`, `GraphicsLayer.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `Modifier` chain (immutable, `then()`-composed) | `UiModifier` data class + extension functions returning `copy(...)` | Faithful | Chaining reads identically (`Modifier.padding(...).width(...)`); internally it's a flat data-class overwrite, not a linked list, but that's an implementation detail invisible at the call site. |
| `Modifier.width`/`.height`/`.size` | `UiModifier.width`/`.height`/`.size` (`LayoutModifiers.kt`) | Faithful | Same fixed-size semantics. |
| `Modifier.fillMaxWidth`/`.fillMaxHeight`/`.fillMaxSize` | Same names (`LayoutModifiers.kt`) | Diverges | Looks identical, but "fill" is resolved per-child against the *parent's configured size*, not against real remaining-constraint math the way Compose's `Constraints` propagation works -- see the `weight()` row below for the concrete failure mode this causes. |
| `Modifier.weight(1f, fill = true)` inside `Row`/`Column` | `UiModifier.weight(weight, fill)` inside `row()`/`column()`, distributed by `resolveWeightedMainAxis()` (`Arrangement.kt`) | Faithful (fixed) | Was a real, already-hit bug class this session (`shadcnField*` controls, checkout-form grid row, `shadcnToggleGroup`) -- `resolveWeightedMainAxis()` used to sum non-weighted siblings' *trial-measured* size into `nonWeightedOccupied`, so a non-weighted `fillMaxWidth()` sibling's trial claim (an artifact of cursor position, not a real reservation) could starve weighted siblings to zero depending on measurement order. Fixed in commit `9455bc51`: a new `fillsMainAxis` signal (threaded through `UiMeasuredContent`/`UiContext`/`RowScope`/`ColumnScope`) now lets the resolver give weighted siblings their proportional share *first* (matching Compose's real constraint-propagation order), then hands non-weighted `FillMax` siblings whatever's left -- which is correctly zero when they're genuinely contending for the same axis, not an order-dependent accident. Verified order-independent via tests in both sibling orderings. The 3 existing `weight(1f)` workarounds at the call sites above were left in place (still correct, just no longer the only option) -- reverting them to `fillMaxWidth()` is a safe, optional cleanup, not required. |
| `Modifier.align(Alignment)` inside `Row`/`Column`/`Box` | `UiModifier.align(UiAlignment)` | Faithful | Per-child cross-axis override, same as Compose's `RowScope.align`/`ColumnScope.align`/`BoxScope.align`. |
| `Modifier.offset(x, y)` | `UiModifier.offset(x, y)` | Faithful | Same additive-post-layout-offset shape. |
| `Modifier.padding(...)` (all four overload shapes) | `UiModifier.padding(...)` (`LayoutModifiers.kt`) | Faithful | Same all/horizontal-vertical/per-edge overload set. |
| `Modifier.background(Color)` / `.border(width, color)` / `.clip(shape)` | `UiModifier.background(Color)` / `.border(width, color)` / `.shape(radius)` (`StyleModifiers.kt`) | Faithful (ergonomics) | Call-site shape matches; internally these route through a separate `Style` object (`styleable()`) rather than being pure per-widget modifier fields -- documented deliberately in `UiModifier.kt`'s own class doc as "modifier is structure/behavior, style is visuals," a split real Compose doesn't make this explicitly. Doesn't change caller-observable behavior. |
| `Modifier.verticalScroll(state)` / `.horizontalScroll(state)` | Same names (`ScrollModifiers.kt`) | Faithful (ergonomics) | Same call shape; both calls just set the same `scrollState`/`scrollConfig` fields, so a modifier chain with both `.verticalScroll(...)` and `.horizontalScroll(...)` silently has the second call overwrite the first (no bidirectional scroll) -- Compose's two functions are independently composable via nested containers, this pair is not. Minor, but a chain like Compose code would naturally write (`.verticalScroll(v).horizontalScroll(h)`) does not do what it looks like. |
| `Modifier.clickable { }` / `Modifier.pointerInput { }` | Not present | Not implemented | No `UiModifier` extension found for click/pointer handling anywhere in `modifier/`. Interactivity in Awake instead flows through `forceHover`/`forceActive`/`forceFocus` fields on `UiModifier` plus `UiScope.hitTest()`/`isActive()`/`tryClaimActive()` (id-based, widget-owned) -- a different ergonomic model than Compose's modifier-attached gesture handlers. Not a bug, just a real gap in modifier-chain-shaped mimicry: a reader expecting `Modifier.clickable` won't find it. |
| `Modifier.graphicsLayer { rotationZ = ...; scaleX = ...; alpha = ... }` | `UiModifier.graphicsLayer(effect: UiGraphicsEffect)` (`GraphicsLayer.kt`) | Diverges | See the dedicated GraphicsLayer section below -- confirmed still true as of this read: it is an effect-marker/tag list, not a real transform. |
| `Modifier.testTag(tag)` | `UiModifier.testTag(tag)` (`StateModifiers.kt`) | Faithful | Same purpose (test-hook id), same shape. |
| `Modifier.zIndex(...)`, `Modifier.rotate/scale/alpha` as top-level modifiers (Compose has both a top-level shorthand and the `graphicsLayer{}` block form) | Not present | Not implemented | Only the `graphicsLayer(effect)` hook exists; no standalone rotate/scale/alpha/zIndex modifier functions. |

## `UiScope`/`row()`/`column()`/`box()` DSL

Source: `layouts/Row.kt`, `Column.kt`, `Box.kt`, `RowScope.kt`, `ColumnScope.kt`,
`BoxScope.kt`, `AbsoluteScope.kt`, `Arrangement.kt`, `Layout.kt`, `RootLayouts.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `Row(horizontalArrangement, verticalAlignment) { }` | `row(horizontalArrangement, verticalAlignment, modifier) { }` (`Row.kt`) | Faithful (ergonomics) | Same named-parameter shape and default (`Arrangement.Start`-equivalent via `defaultArrangement()`), same trailing-lambda-with-scope-receiver call site. |
| `Column(verticalArrangement, horizontalAlignment) { }` | `column(...)` (`Column.kt`) | Faithful (ergonomics) | Same shape. |
| `Box(contentAlignment) { }` | `box(modifier, contentAlignment) { }` (`Box.kt`) | Faithful (ergonomics) | Same shape (`contentAlignment` as a named param, not a modifier). |
| `Arrangement.Start/Center/End/SpaceBetween/SpaceEvenly/SpaceAround/spacedBy(dp)` | Same set, `Arrangement` sealed interface (`Arrangement.kt`) | Faithful | Free-space math for `Center`/`End`/`SpaceBetween`/`SpaceEvenly`/`SpaceAround` in `Arrangement.plan()` matches Compose's own formulas (leading/between space split). |
| Compose's `Constraints`-based measure/layout pass (single measure pass per composition, min/max bounds propagated top-down, `Layout`/`MeasurePolicy`) | A **trial-measure-then-real-measure** two-pass model added for `weight()` support (commit `8f421138`), later fixed for redundant-recursion perf (commit `3f86853e`), partially optimized again in commit `55dd0681`, and given a reusable-trial-context perf fix in a follow-up commit this session | Diverges | Every `row()`/`column()` call with a `WrapContent` axis or any weighted/measured-distribution arrangement pays a throwaway "trial" measurement of its own `content` lambda (`context.measureRowContent`/`measureColumnContent`) purely to learn sizes/weights, then measures again for real placement -- unlike Compose, which measures each child exactly once per composition via `Constraints` negotiation. This is a real perf/behavior difference (side-effecting code inside a `row {}`/`column {}` body, e.g. `animateFloat`, must special-case `isMeasuringInternal()` to avoid double-stepping during the trial pass -- see `UiAnimation.kt`'s explicit guards) that has no Compose analog: a Compose composable body never re-executes to "trial measure" itself this way. **Partial optimization, not a fix of the underlying model** (commit `55dd0681`, see `docs/tasks/2026-08-02-trial-measure-double-execution.md`): real profiling found `UiScope.row()`/`column()` additionally ran its own `hasWeightedChild`-detection trial *unconditionally*, even for `Center`/`End`/`SpaceBetween`/`SpaceEvenly`/`SpaceAround` arrangements (`Arrangement.requiresMeasuredDistribution()`) where that trial's result is provably irrelevant -- those arrangements always take the `plannedSlots` branch regardless of `hasWeightedChild`. Reordering the check to short-circuit the trial in that case cuts per-level content-lambda executions from 3 to 2 for nodes using those five arrangements specifically (a synthetic ui-core benchmark, `TrialMeasureScalingTest`, measured this as a 3^depth -> 2^depth reduction: depth-8 trial count dropped from 86,093,441 to 131,071 in a worst-case nested chain). This does **not** touch the common case -- a plain `Arrangement.Start`/`spacedBy` row or column with a weighted child still pays its own unconditional detection trial, since there's no way to answer "does this content have a weighted child" without executing it once first, and eliminating that requires either a lazy children-gathering phase or per-call-site-id caching, both explicitly scoped out as future, dedicated design work (not attempted here). Real-world impact is arrangement-usage-dependent: ui-showcase's Checkout Form page (the profiling target) uses only `spacedBy`, so its trial count is measurably unchanged by this fix (still 7,696 passes) -- the win is real but currently only reaches pages/components that use the five affected arrangements. **Second, separate fix (this session, per `docs/tasks/2026-08-02-trial-measure-double-execution.md`'s "approach B")**: `UiContextMeasureState.createMeasureContext()` used to allocate a brand-new `UiContext` object graph (plus its `beginFrame`/`pushTextStyle`/`pushFont`/`pushTheme` calls) on *every* trial pass; it now caches and reuses one trial `UiContext` per owning `UiContextMeasureState` instance (scoped 1:1 to whichever real or trial context owns it, never shared across owners, never reentered), resetting its theme/font/textStyle stacks in place instead of pushing onto a fresh stack each time (`UiContextStacks.resetForTrial`). Real measured numbers (new `UiMeasureTrialStats.contextCtorNanos` counter, Checkout Form page, 7,696 passes/frame): construction/`beginFrame`/push cost dropped from 4.516ms to 1.197ms of the total trial-measure time, but that construction cost was itself only ~9.4% of the 48.064ms trial-measure total pre-fix -- so total trial-measure time dropped only modestly, from ~48.06ms to ~44.4-44.7ms (~7% off trial time, ~1-2ms off total frame time; trial *pass count* is unchanged at 7,696, since this fix targets fixed per-trial cost, not pass count). Confirms the original doc's own honest caveat ("a constant-factor win... 20-40% off trial time, unverified") was optimistic -- object-graph construction was real but a minority of trial cost; the large majority is the trial content lambda's own layout/arrangement/text-measurement work, untouched by this fix. The two-pass trial-measure model itself remains unchanged and still diverges from Compose's single-pass `Constraints` propagation for the general case; eliminating the *pass count* (not just fixed per-pass cost) still requires the lazy-children-gathering or per-call-site-id caching work named above, neither attempted here. |
| A `WrapContent` parent's height being influenced by a `FillMax` child's size (Compose: a `wrapContentHeight()` parent constrains children to `Constraints(maxHeight = Infinity)` so a `fillMaxHeight()` child can't inflate it) | Explicitly guarded against via `contributesToWrapHeight`/`contributesToWrapWidth` flags passed to `context.recordMeasuredSlot()` in `RowScope.claimSlot()`/`ColumnScope.claimSlot()` | Faithful (now) | Verified current: `RowScope.claimSlot()` passes `contributesToWrapHeight = height != Dimension.FillMax` and `ColumnScope.claimSlot()` passes `contributesToWrapWidth = width != Dimension.FillMax`, both with inline comments citing this exact failure mode ("task #34"). Commit `83b8a0d1` ("weight() + WrapContent columns no longer collapse/corrupt width") is the fix for this; the current code confirms the guard is in place and this specific corruption is closed, not merely fixed-then-silently-reverted. |
| `Row`/`Column` weighted-child distribution never lets a weighted child's siblings starve to negative/garbage size (Compose clamps via `Constraints`, never produces negative sizes) | `resolveWeightedMainAxis()` `.coerceAtLeast(0f)` on `remaining` | Faithful (edge case) | Confirmed: overflow clamps to `0f` for every weighted child rather than producing negative sizes -- matches Compose's floor-at-zero behavior for this one edge case, even though the general non-weighted-sibling-starves-first behavior above still diverges. |
| `Box`/absolute placement via `Modifier.offset`/`absoluteOffset` inside a `Box` | `AbsoluteScope` + `UiContext.absolute { }` (`AbsoluteScope.kt`, `RootLayouts.kt`) | Not implemented (as a direct analog) | Compose has no dedicated "absolute layout mode" scope the way Awake does -- `AbsoluteScope` is Awake-original (documented in its own KDoc as "the escape hatch for HUD text ... that isn't part of any auto-layout column"), not a mimicked Compose primitive. Listed here for completeness, not as a deviation. |
| `LazyColumn`/`LazyRow` (virtualized/lazy child composition) | Not present | Not implemented | No lazy-list equivalent found under `layouts/`; `verticalScroll`/`horizontalScroll` modifiers exist but drive a plain scroll offset over fully-composed content, not virtualization. |

## Animation primitives

Source: `UiAnimation.kt`, `UiEasing.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `animateFloatAsState(target, animationSpec = spring(...))` | `UiContext.animateFloat(id, target, initial, responsiveness, snapDistance)` | Diverges (ergonomics) | Conceptually the same "chase a target every frame" idea (an exponential-decay spring, `1f - exp(-responsiveness * dt)`), but the call shape is Compose's opposite: `animateFloatAsState` is state-driven (returns a `State<Float>` tied to composition identity, no explicit `id`), while Awake's version is immediate-mode and requires a caller-supplied stable `id` string used as the state-store key (`widgetStateInternal("__animation__$id")`). Forgetting to keep `id` stable across frames (e.g. deriving it from a changing value) silently restarts the animation with no compile-time signal, unlike Compose's automatic call-site/key-based identity. |
| `Animatable<Float>` + `animateTo(target, tween(durationMillis, easing))` | `UiContext.animateFloatTween(id, target, initial, durationMs, easing)` | Diverges (ergonomics) | Same immediate-mode-vs-state-object gap as above; retargeting mid-tween is deliberately matched to Compose's `animateFloatAsState` behavior (restart duration from the current animated value, not jump to `initial` -- confirmed in the function's own doc comment and `retargeted`/`effectiveStart` logic), so retarget semantics are faithful even though the calling convention isn't. |
| `rememberInfiniteTransition()` + `animateFloat(initialValue, targetValue, infiniteRepeatable(tween(...), repeatMode))` | `UiContext.animateFloatRepeatable(id, initialValue, targetValue, durationMs, easing, repeatMode, iterations)` | Faithful (ergonomics), Diverges (mechanism) | Parameter set matches Compose's `infiniteRepeatable`/`repeatable` split (`RepeatMode.Restart`/`Reverse`, `iterations` defaulting to "forever" via `Int.MAX_VALUE`, matching Compose's own `AnimationConstants.Infinite` sentinel pattern per the function's doc comment) -- genuinely faithful ergonomics. Mechanism diverges: progress is computed in **closed form** from an elapsed-time accumulator (`cycleIndex`/`cycleElapsedMs` derived from `elapsedMs / durationMs`) rather than Compose's frame-callback-driven `Animatable`; this is called out in-code as a deliberate choice to avoid a "one-frame-late flip" stutter bug the naive port had, not an oversight. |
| `AnimationSpec`/`tween`/`spring` as a reusable, composable value object (constructed once, passed around) | Two free functions (`animateFloatTween`, `animateFloat`) each taking their spec inline as parameters (`durationMs`, `easing`, `responsiveness`) | Diverges | Compose lets you build an `AnimationSpec` once and reuse/compose it (`repeatable(spring(...))`, pass the same spec to multiple `animateXAsState` calls). Awake has no equivalent value type -- each call site repeats its own `durationMs`/`easing`/`responsiveness` literals; `animateFloatRepeatable` is its own separate function rather than a `repeatable()` wrapper *around* `animateFloatTween`'s spec, even though the doc comment explicitly likens it to that Compose wrapping pattern. |
| `Easing` fun-interface + `LinearEasing`/`FastOutSlowInEasing`/`CubicBezierEasing` | `Easing` fun-interface + `LinearEasing`/`EaseIn`/`EaseOut`/`EaseInOut`/`CubicBezierEasing` (`UiEasing.kt`) | Faithful | Same fun-interface shape (`fun transform(fraction: Float): Float`, mirrored explicitly in the KDoc), same cubic-bezier Newton-Raphson-with-bisection-fallback solving approach Compose/WebKit use, same CSS-named preset curves (though named/pinned to CSS `ease-in`/`ease-out`/`ease-in-out` control points rather than Compose's own named `FastOutSlowInEasing` etc. -- equivalent shape, different preset library). |
| `updateTransition` / `MutableTransitionState` (multi-property, state-machine-driven transitions) | Not present | Not implemented | No multi-property transition coordinator; each `animateFloat*` call is independent. |
| Trial-measurement passes must not double-step a side-effecting animation (no Compose analog needed -- Compose has no "trial measure" concept) | Every `animateFloat*` function explicitly checks `isMeasuringInternal()` and returns the already-stored value without advancing state during a trial pass | Diverges (necessarily) | This guard exists purely because of the Row/Column trial-measurement divergence documented above -- it's a deviation forced by Awake's own two-pass layout model, not something a Compose port would ever need. The code comments explicitly reference an already-fixed real bug class for this exact issue (shimmer, commit `85f14821`), so treat any *new* side-effecting `UiContext` state read/write as needing the same guard, not just the three functions already covering it. |

## `graphicsLayer`

Source: `modifier/GraphicsLayer.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `Modifier.graphicsLayer { rotationZ = 45f; scaleX = 1.2f; scaleY = 1.2f; alpha = 0.5f; shadowElevation = 4f; clip = true; ... }` | `UiModifier.graphicsLayer(effect: UiGraphicsEffect)` + `UiGraphicsLayer(effects: List<UiGraphicsEffect>)` | Diverges | Confirmed by re-reading the current file: this is **only an effect-marker/tag hook**, not a real transform. `UiGraphicsEffect` is an empty marker `interface` with zero properties; `UiGraphicsLayer` is just a `List<UiGraphicsEffect>` with `then()`/`has<T>()`/`without<T>()` set-composition helpers. There is no `rotationZ`, `scaleX`/`scaleY`, `alpha`, `translationX`/`Y`, `shadowElevation`, or `clip` field anywhere in this file or type. The file's own KDoc says as much: "`ui-core` only owns this contract and does not know how to draw any effect; concrete effects ... are shadcn-compose-style extensions layered on top." Concretely, only one real effect currently exists in the codebase built on this hook: `UiShimmerEffect` (a zero-property marker `data object`, see `StyleModifiers.kt`'s `shadcnShimmer()`) -- consuming widgets check `modifier.shimmer` (`graphicsLayer?.has<UiShimmerEffect>()`) and draw their own animated opacity pulse; the "graphicsLayer" hook itself carries no numeric transform data for them to read. A caller writing `Modifier.graphicsLayer { rotationZ = 45f }`-style code against this API is not possible -- the call shape is fundamentally `graphicsLayer(SomeMarkerEffect)`, not a configuration-lambda block, so this also diverges in call *shape*, not just capability. |
| Real per-pixel rotation/scale/alpha compositing in the render pipeline | Not present | Not implemented | No rotation matrix, scale transform, or alpha blend tied to `graphicsLayer` exists in `ui-core`; any widget wanting a visual transform must either hand-roll it in its own draw call or (as shimmer does) interpret a marker effect and paint a bespoke effect itself. Confirms the pre-existing note from earlier this session is still accurate as of this read -- nothing has changed this in the meantime. |

## Tally

- **Modifier**: 9 Faithful (`weight()`+`fillMax*` starvation fixed in commit `9455bc51`, moved from Diverges), 2 Diverges (scroll-modifier overwrite, `graphicsLayer`), 2 Not implemented (`clickable`/`pointerInput`, standalone rotate/scale/alpha/zIndex)
- **Scope/DSL**: 4 Faithful, 2 Diverges (two-pass trial-measure model -- partially optimized in commit `55dd0681` for `Center`/`End`/`SpaceBetween`/`SpaceEvenly`/`SpaceAround` arrangements, still diverges in the general case; the now-fixed-but-noteworthy wrap-height-corruption history), 2 Not implemented (`AbsoluteScope` as non-analog, `LazyColumn`/`LazyRow`)
- **Animation**: 2 Faithful (`animateFloatRepeatable` ergonomics, `Easing`), 4 Diverges (`animateFloat` call shape, `animateFloatTween` call shape, no reusable `AnimationSpec` value type, forced trial-measurement guard), 1 Not implemented (`updateTransition`)
- **GraphicsLayer**: 0 Faithful, 1 Diverges (marker-hook vs. real transform block), 1 Not implemented (real transform compositing)

The `weight()` + `fillMaxWidth()`/`fillMaxHeight()` starvation that used to be the single
most load-bearing "looks safe, isn't" finding here is fixed as of commit `9455bc51` --
mixing `weight()` and `FillMax` siblings in the same `row()`/`column()` now resolves in
Compose's real order (weighted siblings first, `FillMax` leftovers last) instead of
being order-dependent. The most load-bearing remaining finding is `graphicsLayer` being
a marker-tag system with zero real transform fields, since its Compose name strongly
implies rotation/scale/alpha support that doesn't exist.
