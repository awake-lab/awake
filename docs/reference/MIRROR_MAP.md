# Mirror Map: Awake UI DSL vs. Jetpack Compose

Awake's `ui-core` DSL (`UiModifier`, `row()`/`column()`/`box()`, `animateFloat*`,
`graphicsLayer`) is deliberately shaped to *feel* like Jetpack Compose -- chainable
modifiers, slot-lambda scopes, `weight()`, `animateFloatAsState`-style helpers -- so that
a Compose developer's muscle memory transfers. It is not a Compose-compiler-plugin
runtime: there is no recomposition, no snapshot state, no constraint negotiation.
Following `kotlin-multiplatform-api-mimicry`'s method, this doc catalogs each mimicked
primitive against Compose's real current public shape and calls out three states:
**Faithful** (same ergonomics, same behavior a Compose developer would expect),
**Diverges** (looks Compose-shaped but behaves differently -- the dangerous category,
since it passes a glance-review and then causes a layout/render bug later), and
**Not implemented** (a real gap, not necessarily a deviation). Every row below is backed
by a direct read of the current source under
`awake/engine/ui/ui-core/src/commonMain/kotlin/io/github/ronjunevaldoz/awake/ui/`, not
memory of Compose or of this codebase from an earlier session.

Use this doc before reaching for a Compose idiom in Awake code: check whether the row
below says "Faithful" (safe to assume Compose semantics) or "Diverges" (read the
deviation detail first).

## `UiModifier`

Source: `modifier/UiModifier.kt`, `LayoutModifiers.kt`, `StyleModifiers.kt`,
`ScrollModifiers.kt`, `StateModifiers.kt`, `GraphicsLayer.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `Modifier` chain (immutable, `then()`-composed) | `UiModifier` data class + extension functions returning `copy(...)` | Faithful | Chaining reads identically (`Modifier.padding(...).width(...)`); internally it's a flat data-class overwrite, not a linked list, but that's an implementation detail invisible at the call site. |
| `Modifier.width`/`.height`/`.size` | `UiModifier.width`/`.height`/`.size` (`LayoutModifiers.kt`) | Faithful | Same fixed-size semantics. |
| `Modifier.fillMaxWidth`/`.fillMaxHeight`/`.fillMaxSize` | Same names (`LayoutModifiers.kt`) | Diverges | Looks identical, but "fill" is resolved per-child against the *parent's configured size*, not against real remaining-constraint math the way Compose's `Constraints` propagation works -- see the `weight()` row below for the concrete failure mode this causes. |
| `Modifier.weight(1f, fill = true)` inside `Row`/`Column` | `UiModifier.weight(weight, fill)` inside `row()`/`column()`, distributed by `resolveWeightedMainAxis()` (`Arrangement.kt`) | Faithful (fixed) | Was a real, already-hit bug class this session (`shadcnField*` controls, checkout-form grid row, `shadcnToggleGroup`) -- `resolveWeightedMainAxis()` used to sum non-weighted siblings' *trial-measured* size into `nonWeightedOccupied`, so a non-weighted `fillMaxWidth()` sibling's trial claim (an artifact of cursor position, not a real reservation) could starve weighted siblings to zero depending on measurement order. Fixed in commit `9455bc51`: a new `fillsMainAxis` signal (threaded through `UiMeasuredContent`/`UiContext`/`RowScope`/`ColumnScope`) now lets the resolver give weighted siblings their proportional share *first* (matching Compose's real constraint-propagation order), then hands non-weighted `FillMax` siblings whatever's left -- which is correctly zero when they're genuinely contending for the same axis, not an order-dependent accident. Verified order-independent via tests in both sibling orderings. The 3 existing `weight(1f)` workarounds at the call sites above were left in place (still correct, just no longer the only option) -- reverting them to `fillMaxWidth()` is a safe, optional cleanup, not required. |
| `Modifier.align(Alignment)` inside `Row`/`Column`/`Box` | `UiModifier.align(UiAlignment)` | Faithful | Per-child cross-axis override, same as Compose's `RowScope.align`/`ColumnScope.align`/`BoxScope.align`. |
| `Modifier.offset(x, y)` | `UiModifier.offset(x, y)` | Faithful | Same additive-post-layout-offset shape. |
| `Modifier.padding(...)` (all four overload shapes) | `UiModifier.padding(...)` (`LayoutModifiers.kt`) | Faithful | Same all/horizontal-vertical/per-edge overload set. |
| `Modifier.background(Color)` / `.border(width, color)` / `.clip(shape)` | `UiModifier.background(Color)` / `.border(width, color)` / `.shape(radius)` (`StyleModifiers.kt`) | Faithful (ergonomics) | Call-site shape matches; internally these route through a separate `Style` object (`styleable()`) rather than being pure per-widget modifier fields -- documented deliberately in `UiModifier.kt`'s own class doc as "modifier is structure/behavior, style is visuals," a split real Compose doesn't make this explicitly. Doesn't change caller-observable behavior. |
| `Modifier.verticalScroll(state)` / `.horizontalScroll(state)` | Same names (`ScrollModifiers.kt`) | Faithful (ergonomics) | Same call shape; both calls just set the same `scrollState`/`scrollConfig` fields, so a modifier chain with both `.verticalScroll(...)` and `.horizontalScroll(...)` silently has the second call overwrite the first (no bidirectional scroll) -- Compose's two functions are independently composable via nested containers, this pair is not. Minor, but a chain like Compose code would naturally write (`.verticalScroll(v).horizontalScroll(h)`) does not do what it looks like. **Real default-styling bug found and fixed (this session, `ScrollContainers.kt`'s `scrollPanel()`)**: `column(id, modifier = Modifier.verticalScroll(state))` with no `style` at all silently rendered as a themed card -- border + `card` background -- because `scrollPanel()` unconditionally passed `defaults = currentTheme.components.surface` into `resolveStyle`, regardless of whether the caller's own style resolved any visuals. The non-scroll column path (`resolveMeasuredColumn`, gated by `smartColumn`'s `hasResolvedVisuals` check) never had this problem -- a bare non-scroll `column()` stays invisible unless its own `style` asks for a background/border. In Compose, `Modifier.verticalScroll()` never paints anything by itself; this divergence had no Compose analog and no signature-diff-based audit pass could have caught it, since the API *shape* (`verticalScroll(state)`, same name, same param) was already faithful -- the bug was purely in *default runtime behavior* baked into an internal `defaults =` argument, invisible to a pure API-surface comparison. Fixed by changing `scrollPanel()`'s `defaults` to the same neutral `Style { shape(UiShape.md); borderWidth(UiShape.none) }` base `surface()` (`layouts/Surface.kt`) already uses -- a bare scroll column now stays invisible by default like its non-scroll counterpart, and only paints when the caller's own `style` sets a background/border. |
| `Modifier.clickable(enabled, onClick)` | `UiModifier.clickable(enabled, onClick)` (`ClickableModifiers.kt`), resolved via `UiScope.resolveClickable(id, slot, modifier)` | Diverges | Call shape (`Modifier.clickable(enabled = ..., onClick = { ... })`) and click semantics (must press *and* release inside the same bounds, matching `button`/`checkbox`'s existing `interact()` press-release-inside behavior in `ui-headless`) are faithful. What diverges: Compose's `Modifier.clickable` works on *any* composable automatically, because Compose's pointer-input pipeline is wired to every layout node by the framework. Awake's version does not -- it's an opt-in field (`UiModifier.clickAction`) that a widget's own implementation must explicitly resolve by calling `resolveClickable(id, slot, modifier)` at the same point it already resolves `forceHover`/`forceActive`/`forceFocus`, using that widget's own stable `id` as the active-state key (Awake's click detection is id-based via `tryClaimActive`/`isActive`, not automatic per-composable identity the way Compose's is). Piloted on `surface()` (`ui-core/layouts/Surface.kt`) -- chosen because `surface()` had *zero* built-in click semantics before this (unlike `button`/`checkbox`, which already hand-roll their own `interact()` call and were deliberately left unmigrated, out of scope for this pass), so it's the clearest proof the mechanism works standalone via the modifier alone. Built entirely on top of the pre-existing `hitTest()`/`tryClaimActive()`/`isActive()`/`releaseActiveIfMatches()` primitives -- not a parallel input pipeline. No `Modifier.pointerInput { }` escape hatch was added (YAGNI -- no real call site needed raw press/drag/move tracking yet; add one if/when a consumer needs lower-level gesture data than `clickable` exposes). |
| `Modifier.graphicsLayer { rotationZ = ...; scaleX = ...; alpha = ... }` | `UiModifier.graphicsLayer(effect: UiGraphicsEffect)` (`GraphicsLayer.kt`) | Diverges (partially, alpha and scale are real) | See the dedicated GraphicsLayer section below -- `UiAlphaEffect` and `UiScaleEffect` now carry real values applied at `UiContext`'s emission choke point (alpha CPU-side, scale GPU-side), but rotation/shadowElevation/clip-transform are still not implemented and the call shape is still `graphicsLayer(SomeEffect)`, not a configuration lambda. |
| `Modifier.testTag(tag)` | `UiModifier.testTag(tag)` (`StateModifiers.kt`) | Faithful | Same purpose (test-hook id), same shape. |
| `Modifier.zIndex(...)`, `Modifier.rotate/scale/alpha` as top-level modifiers (Compose has both a top-level shorthand and the `graphicsLayer{}` block form) | `UiModifier.alpha(value)` / `UiModifier.scale(scaleX, scaleY, pivotX, pivotY)` (`GraphicsLayer.kt`) exist as standalone shorthands; rotate/zIndex do not | Diverges (alpha, scale), Not implemented (rotate/zIndex) | `alpha(value)` and `scale(...)` are real (build a `UiAlphaEffect`/`UiScaleEffect`), matching Compose's top-level-shorthand ergonomics. No standalone rotate/zIndex modifier functions exist. |

## `UiScope`/`row()`/`column()`/`box()` DSL

Source: `layouts/Row.kt`, `Column.kt`, `Box.kt`, `RowScope.kt`, `ColumnScope.kt`,
`BoxScope.kt`, `AbsoluteScope.kt`, `Arrangement.kt`, `Layout.kt`, `RootLayouts.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `Row(horizontalArrangement, verticalAlignment) { }` | `row(horizontalArrangement, verticalAlignment, modifier) { }` (`Row.kt`) | Faithful (ergonomics) | Same named-parameter shape and default (`Arrangement.Start`-equivalent via `defaultArrangement()`), same trailing-lambda-with-scope-receiver call site. |
| `Column(verticalArrangement, horizontalAlignment) { }` | `column(...)` (`Column.kt`) | Faithful (ergonomics) | Same shape. |
| `Box(contentAlignment) { }` | `box(modifier, contentAlignment) { }` (`Box.kt`) | Faithful (ergonomics) | Same shape (`contentAlignment` as a named param, not a modifier). |
| `Arrangement.Start/Center/End/SpaceBetween/SpaceEvenly/SpaceAround/spacedBy(dp)` | Same set, `Arrangement` sealed interface (`Arrangement.kt`) | Faithful | Free-space math for `Center`/`End`/`SpaceBetween`/`SpaceEvenly`/`SpaceAround` in `Arrangement.plan()` matches Compose's own formulas (leading/between space split). |
| Compose's `Constraints`-based measure/layout pass (single measure pass per composition, min/max bounds propagated top-down, `Layout`/`MeasurePolicy`) | A **trial-measure-then-real-measure** two-pass model added for `weight()` support (commit `8f421138`), later fixed for redundant-recursion perf (commit `3f86853e`), partially optimized again in commit `55dd0681`, and given a reusable-trial-context perf fix in a follow-up commit this session | Diverges | Every `row()`/`column()` call with a `WrapContent` axis or any weighted/measured-distribution arrangement pays a throwaway "trial" measurement of its own `content` lambda (`context.measureRowContent`/`measureColumnContent`) purely to learn sizes/weights, then measures again for real placement -- unlike Compose, which measures each child exactly once per composition via `Constraints` negotiation. This is a real perf/behavior difference (side-effecting code inside a `row {}`/`column {}` body, e.g. `animateFloat`, must special-case `isMeasuringInternal()` to avoid double-stepping during the trial pass -- see `UiAnimation.kt`'s explicit guards) that has no Compose analog: a Compose composable body never re-executes to "trial measure" itself this way. **Partial optimization, not a fix of the underlying model** (commit `55dd0681`, see `docs/tasks/archive/2026-08-02-trial-measure-double-execution.md`): real profiling found `UiScope.row()`/`column()` additionally ran its own `hasWeightedChild`-detection trial *unconditionally*, even for `Center`/`End`/`SpaceBetween`/`SpaceEvenly`/`SpaceAround` arrangements (`Arrangement.requiresMeasuredDistribution()`) where that trial's result is provably irrelevant -- those arrangements always take the `plannedSlots` branch regardless of `hasWeightedChild`. Reordering the check to short-circuit the trial in that case cuts per-level content-lambda executions from 3 to 2 for nodes using those five arrangements specifically (a synthetic ui-core benchmark, `TrialMeasureScalingTest`, measured this as a 3^depth -> 2^depth reduction: depth-8 trial count dropped from 86,093,441 to 131,071 in a worst-case nested chain). This does **not** touch the common case -- a plain `Arrangement.Start`/`spacedBy` row or column with a weighted child still pays its own unconditional detection trial, since there's no way to answer "does this content have a weighted child" without executing it once first, and eliminating that requires either a lazy children-gathering phase or per-call-site-id caching, both explicitly scoped out as future, dedicated design work (not attempted here). Real-world impact is arrangement-usage-dependent: ui-showcase's Checkout Form page (the profiling target) uses only `spacedBy`, so its trial count is measurably unchanged by this fix (still 7,696 passes) -- the win is real but currently only reaches pages/components that use the five affected arrangements. **Second, separate fix (this session, per `docs/tasks/archive/2026-08-02-trial-measure-double-execution.md`'s "approach B")**: `UiContextMeasureState.createMeasureContext()` used to allocate a brand-new `UiContext` object graph (plus its `beginFrame`/`pushTextStyle`/`pushFont`/`pushTheme` calls) on *every* trial pass; it now caches and reuses one trial `UiContext` per owning `UiContextMeasureState` instance (scoped 1:1 to whichever real or trial context owns it, never shared across owners, never reentered), resetting its theme/font/textStyle stacks in place instead of pushing onto a fresh stack each time (`UiContextStacks.resetForTrial`). Real measured numbers (new `UiMeasureTrialStats.contextCtorNanos` counter, Checkout Form page, 7,696 passes/frame): construction/`beginFrame`/push cost dropped from 4.516ms to 1.197ms of the total trial-measure time, but that construction cost was itself only ~9.4% of the 48.064ms trial-measure total pre-fix -- so total trial-measure time dropped only modestly, from ~48.06ms to ~44.4-44.7ms (~7% off trial time, ~1-2ms off total frame time; trial *pass count* is unchanged at 7,696, since this fix targets fixed per-trial cost, not pass count). Confirms the original doc's own honest caveat ("a constant-factor win... 20-40% off trial time, unverified") was optimistic -- object-graph construction was real but a minority of trial cost; the large majority is the trial content lambda's own layout/arrangement/text-measurement work, untouched by this fix. The two-pass trial-measure model itself remains unchanged and still diverges from Compose's single-pass `Constraints` propagation for the general case; eliminating the *pass count* (not just fixed per-pass cost) still requires the lazy-children-gathering or per-call-site-id caching work named above. **Third fix, the per-call-site-id caching work itself (this session, `docs/tasks/archive/2026-08-02-trial-measure-cross-frame-cache.md`)**: `UiScope.row()`/`UiScope.column()` gained opt-in `id`/`cacheKey` parameters (mirroring `animateFloat(id, ...)`'s identity model, `UiAnimation.kt`) that cache *only* the `hasWeightedChild` boolean -- never sizes/positions, to avoid reintroducing the staleness class `WrapContentMeasurementStateTest` guards against -- across frames in the real widget-state store, skipping the detection trial entirely on a cache hit. Both default to `null`; every pre-existing call site is unaffected. A debug/test-only consistency check (`UiWeightCacheConsistencyCheck.enabled`, off by default, same zero-cost-when-disabled contract as `UiMeasureTrialStats.enabled`) re-runs the real trial on every cache hit and throws if it disagrees with the cached answer, catching a caller's stale `cacheKey` loudly in tests instead of shipping wrong layout silently -- verified by `RowColumnWeightCacheTest`'s three cases (cache-hit, cache-invalidation, stale-key-caught-by-consistency-check). Confirmed real adoption cost, not free: only `UiScope.row()`/`column()` accept the parameters directly, and reaching them from ordinary nested DSL usage (which resolves to the `ColumnScope`/`RowScope`/`AbsoluteScope`/`BoxScope` wrapper overloads) required threading `id`/`cacheKey` through those wrapper functions too -- a deliberate, additive expansion beyond the design doc's literal "wrappers don't need this" text, made necessary because direct inspection of `samples/ui-showcase` found *no* real call site that could reach `UiScope.row()`/`column()` without it (every shell/sidebar row/column is written inside a `BoxScope`/`ColumnScope` receiver). Piloted on `samples/ui-showcase`'s persistent shell (`UiShowcaseUi.kt`'s outer `row(id = "ui-showcase-shell-row", cacheKey = "static", ...)` and compact-mode `column(id = "ui-showcase-mobile-shell", cacheKey = "static", ...)`, plus `UiShowcaseChrome.kt`'s Preview/Code tabs row) -- each given a constant `cacheKey` because their direct children never call `.weight()` anywhere in the fixed source, so the cached answer can never go stale; the two content-viewport `column(id = "ui-showcase-*-content-viewport", ...)` calls were deliberately left unmigrated because they set `verticalScroll`, routing through `smartColumn`'s scrollable-container branch (`scrollPanel`) rather than `resolveMeasuredColumn` -- the only strategy this cache's `cacheKey` is wired into -- so `cacheKey` there would be accepted but silently do nothing. **Real measured number** (`UiShowcaseLayoutCostTest.measureShellRowCacheImpact`, steady-state, Checkout Form page): caching just the one outer shell row's `hasWeightedChild` trial cut per-frame trial-pass count from 15,381 to 7,690 (-50.0%) -- a large win from one call site because that row sits at the tree's root, so its own throwaway trial re-executes the *entire* shell subtree underneath it (sidebar + full page content) exactly once extra; removing that one redundant top-level trial removes a redundant execution of everything nested inside it. This does not change the Checkout Form page's own total trial count as reported by `measureRealShellFrameCost` (still ~7,690 -- that number was already *post*-cache, since `drawRealShowcaseShell`'s default `cacheShellRow = true` mirrors the shipped migration), confirming the win is real but, as the design doc predicted, gated on migrating individual call sites by hand -- the shell/sidebar's own internal `row()`/`column()` calls (inside `drawUiShowcaseSidebar`, `shadcnSidebar`, `shadcnSurface`) remain unmigrated (either no direct `row()`/`column()` call exists there, or -- for `shadcnSidebar`/`shadcnSurface` -- they resolve to `resolveVisualSurface`'s surface-styling branch, also outside `cacheKey`'s wiring, and out of `ui-core`'s ownership to touch here regardless). |
| A `WrapContent` parent's height being influenced by a `FillMax` child's size (Compose: a `wrapContentHeight()` parent constrains children to `Constraints(maxHeight = Infinity)` so a `fillMaxHeight()` child can't inflate it) | Explicitly guarded against via `contributesToWrapHeight`/`contributesToWrapWidth` flags passed to `context.recordMeasuredSlot()` in `RowScope.claimSlot()`/`ColumnScope.claimSlot()` | Faithful (now) | Verified current: `RowScope.claimSlot()` passes `contributesToWrapHeight = height != Dimension.FillMax` and `ColumnScope.claimSlot()` passes `contributesToWrapWidth = width != Dimension.FillMax`, both with inline comments citing this exact failure mode ("task #34"). Commit `83b8a0d1` ("weight() + WrapContent columns no longer collapse/corrupt width") is the fix for this; the current code confirms the guard is in place and this specific corruption is closed, not merely fixed-then-silently-reverted. |
| `Row`/`Column` weighted-child distribution never lets a weighted child's siblings starve to negative/garbage size (Compose clamps via `Constraints`, never produces negative sizes) | `resolveWeightedMainAxis()` `.coerceAtLeast(0f)` on `remaining` | Faithful (edge case) | Confirmed: overflow clamps to `0f` for every weighted child rather than producing negative sizes -- matches Compose's floor-at-zero behavior for this one edge case, even though the general non-weighted-sibling-starves-first behavior above still diverges. |
| `Box`/absolute placement via `Modifier.offset`/`absoluteOffset` inside a `Box` | `AbsoluteScope` + `UiContext.absolute { }` (`AbsoluteScope.kt`, `RootLayouts.kt`) | Not implemented (as a direct analog) | Compose has no dedicated "absolute layout mode" scope the way Awake does -- `AbsoluteScope` is Awake-original (documented in its own KDoc as "the escape hatch for HUD text ... that isn't part of any auto-layout column"), not a mimicked Compose primitive. Listed here for completeness, not as a deviation. |
| `LazyColumn`/`LazyRow` (virtualized/lazy child composition) | `lazyColumn(id, itemCount, itemHeight, modifier, key, itemContent)` / `lazyRow(...)` (`layouts/LazyList.kt`) | Diverges | Real virtualization now exists -- only items whose bounds intersect the viewport (plus a 2-item default overscan) run `itemContent` and emit primitives; a 10,000-item `lazyColumn` in a 300px-tall viewport composes 13 items (13 `Quad` primitives out of 15 total), confirmed by `LazyColumnVirtualizationTest`. Shape diverges from Compose's `LazyColumn { items(count, key) { index -> ... } }` in two deliberate ways: (1) every item must share one caller-supplied fixed `itemHeight`/`itemWidth` (`Dp`) rather than Compose's per-item lazy real measurement -- picked over a measure-and-cache-per-id model specifically to avoid re-triggering Awake's existing trial-measure double-execution cost (`docs/tasks/archive/2026-08-02-trial-measure-double-execution.md`) for every item scrolled into view; total content extent is pure arithmetic (`itemCount * itemHeight`), zero measurement of any item, on- or off-screen; (2) scroll state is an explicit `Modifier.verticalScroll(state)`/`horizontalScroll(state)` argument (reusing `ScrollContainers.kt`'s existing `UiScrollState`, not a new lazy-list-owned scroll model), where Compose's `LazyListState` is list-owned. `key` is threaded into `itemContent(index, key)` (unlike Compose, which keeps `key` internal to its slot-reuse machinery) so callers can build stable nested widget ids (`checkbox(id = "todo-$key", ...)`) -- Awake's immediate-mode `WidgetState` is keyed purely by the id string a widget receives and off-screen indices are simply skipped (never recycled into a different index's slot), so this is a convenience for callers building correct ids, not a state-corruption fix the way Compose's `key` is. |

## Animation primitives

Source: `UiAnimation.kt`, `UiEasing.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `animateFloatAsState(target, animationSpec = spring(...))` | `UiContext.animateFloat(id, target, initial, responsiveness, snapDistance)` | Diverges (ergonomics) | Conceptually the same "chase a target every frame" idea (an exponential-decay spring, `1f - exp(-responsiveness * dt)`), but the call shape is Compose's opposite: `animateFloatAsState` is state-driven (returns a `State<Float>` tied to composition identity, no explicit `id`), while Awake's version is immediate-mode and requires a caller-supplied stable `id` string used as the state-store key (`widgetStateInternal("__animation__$id")`). Forgetting to keep `id` stable across frames (e.g. deriving it from a changing value) silently restarts the animation with no compile-time signal, unlike Compose's automatic call-site/key-based identity. |
| `Animatable<Float>` + `animateTo(target, tween(durationMillis, easing))` | `UiContext.animateFloatTween(id, target, initial, durationMs, easing)` | Diverges (ergonomics) | Same immediate-mode-vs-state-object gap as above; retargeting mid-tween is deliberately matched to Compose's `animateFloatAsState` behavior (restart duration from the current animated value, not jump to `initial` -- confirmed in the function's own doc comment and `retargeted`/`effectiveStart` logic), so retarget semantics are faithful even though the calling convention isn't. |
| `rememberInfiniteTransition()` + `animateFloat(initialValue, targetValue, infiniteRepeatable(tween(...), repeatMode))` | `UiContext.animateFloatRepeatable(id, initialValue, targetValue, durationMs, easing, repeatMode, iterations)` | Faithful (ergonomics), Diverges (mechanism) | Parameter set matches Compose's `infiniteRepeatable`/`repeatable` split (`RepeatMode.Restart`/`Reverse`, `iterations` defaulting to "forever" via `Int.MAX_VALUE`, matching Compose's own `AnimationConstants.Infinite` sentinel pattern per the function's doc comment) -- genuinely faithful ergonomics. Mechanism diverges: progress is computed in **closed form** from an elapsed-time accumulator (`cycleIndex`/`cycleElapsedMs` derived from `elapsedMs / durationMs`) rather than Compose's frame-callback-driven `Animatable`; this is called out in-code as a deliberate choice to avoid a "one-frame-late flip" stutter bug the naive port had, not an oversight. |
| `AnimationSpec`/`tween`/`spring` as a reusable, composable value object (constructed once, passed around) | Two free functions (`animateFloatTween`, `animateFloat`) each taking their spec inline as parameters (`durationMs`, `easing`, `responsiveness`) | Diverges | Compose lets you build an `AnimationSpec` once and reuse/compose it (`repeatable(spring(...))`, pass the same spec to multiple `animateXAsState` calls). Awake has no equivalent value type -- each call site repeats its own `durationMs`/`easing`/`responsiveness` literals; `animateFloatRepeatable` is its own separate function rather than a `repeatable()` wrapper *around* `animateFloatTween`'s spec, even though the doc comment explicitly likens it to that Compose wrapping pattern. |
| `Easing` fun-interface + `LinearEasing`/`FastOutSlowInEasing`/`CubicBezierEasing` | `Easing` fun-interface + `LinearEasing`/`EaseIn`/`EaseOut`/`EaseInOut`/`CubicBezierEasing` (`UiEasing.kt`) | Faithful | Same fun-interface shape (`fun transform(fraction: Float): Float`, mirrored explicitly in the KDoc), same cubic-bezier Newton-Raphson-with-bisection-fallback solving approach Compose/WebKit use, same CSS-named preset curves (though named/pinned to CSS `ease-in`/`ease-out`/`ease-in-out` control points rather than Compose's own named `FastOutSlowInEasing` etc. -- equivalent shape, different preset library). |
| `updateTransition` / `MutableTransitionState` (multi-property, state-machine-driven transitions) | `UiContext.rememberTransition(id, targetState, durationMs, easing)` (`UiTransition.kt`) | Diverges (ergonomics, scope) | Real, not a stub: a stable `id`-keyed 0f-1f progress value that anchors the first-seen `targetState` as 0f and tweens to 1f (and back) whenever `targetState` compares unequal to that anchor, sharing one `animateFloatTween` lifecycle a caller derives N properties from via plain lerp math. Deliberately scoped down from Compose's real API: no per-property child registration (`transition.animateFloat { state -> ... }`) that lets multiple independently-configured properties register against one coordinator object -- that needs real multi-child bookkeeping the existing id-per-value `WidgetState` store doesn't cleanly support without a larger `UiAnimation.kt` refactor, so it was deferred rather than half-built. Calling it more than once per frame with the same `id` double-steps the underlying tween (same caveat `animateFloatTween` already has); the intended usage is one call per frame, then deriving multiple properties from the single returned float. No-ops during a trial-measurement pass "for free" by delegating all stepping to `animateFloatTween`'s existing `isMeasuringInternal()` guard -- it introduces no side-effecting state of its own. |
| Trial-measurement passes must not double-step a side-effecting animation (no Compose analog needed -- Compose has no "trial measure" concept) | Every `animateFloat*` function explicitly checks `isMeasuringInternal()` and returns the already-stored value without advancing state during a trial pass | Diverges (necessarily) | This guard exists purely because of the Row/Column trial-measurement divergence documented above -- it's a deviation forced by Awake's own two-pass layout model, not something a Compose port would ever need. The code comments explicitly reference an already-fixed real bug class for this exact issue (shimmer, commit `85f14821`), so treat any *new* side-effecting `UiContext` state read/write as needing the same guard, not just the three functions already covering it. |

## `graphicsLayer`

Source: `modifier/GraphicsLayer.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `Modifier.graphicsLayer { rotationZ = 45f; scaleX = 1.2f; scaleY = 1.2f; alpha = 0.5f; shadowElevation = 4f; clip = true; ... }` | `UiModifier.graphicsLayer(effect: UiGraphicsEffect)` + `UiGraphicsLayer(effects: List<UiGraphicsEffect>)` | Diverges | `UiGraphicsEffect` is still an empty marker `interface`, and `UiGraphicsLayer` is still just a `List<UiGraphicsEffect>` with `then()`/`has<T>()`/`without<T>()` set-composition helpers -- concrete effects (alpha, shimmer) are still layered on top rather than fields on the layer itself. A caller writing `Modifier.graphicsLayer { rotationZ = 45f }`-style configuration-lambda code against this API is still not possible -- the call shape is `graphicsLayer(SomeEffect)`, not a lambda block. What's changed since the previous read: one of those effects, `UiAlphaEffect(alpha: Float)`, now carries a real value instead of being a zero-property marker like `UiShimmerEffect` -- see the alpha-compositing row below. |
| Real per-pixel alpha compositing in the render pipeline | `UiAlphaEffect(alpha)` (`GraphicsLayer.kt`) applied by `UiContext.pushGraphicsLayerAlphaInternal`/`popGraphicsLayerAlphaInternal` (`UiAnimatedVisibility.kt`'s `withGraphicsLayerAlpha`), multiplied into every emitted primitive's color at `UiContext.emitInternal`/`emitOverlayInternal` via `UiDrawPrimitive.scaledByAlpha` | Faithful (alpha only) | Real, not a marker -- `withGraphicsLayerAlpha(alpha) { block() }` pushes onto a stacked alpha value (nested layers multiply, matching real compositing) that every primitive emitted anywhere inside `block()`, at any composite-widget nesting depth, has multiplied into its `Color.a` at the one central emission choke point -- no per-widget/per-renderer changes were needed, since every `UiDrawPrimitive` already carried its own `Color`. This is a CPU-side per-primitive alpha pre-multiply, not a real offscreen-buffer-then-blend compositing pass, so it's correct for fading a subtree in/out (the actual use case -- see `animatedVisibility` below and `UiPopup.kt`'s fade) but not for correctly blending overlapping semi-transparent content *within* one faded subtree. `animatedVisibility(id, visible, durationMs, easing, content)` (`UiAnimatedVisibility.kt`) is the real `AnimatedVisibility`-equivalent built on top of this: it drives the alpha via the existing `animateFloatTween` mechanism and keeps calling `content()` through the exit fade (instead of unmounting the frame `visible` flips false) until the tween settles at zero. |
| Real per-pixel scale compositing in the render pipeline | `UiScaleEffect(scaleX, scaleY, pivotX, pivotY)` (`GraphicsLayer.kt`) applied by `UiContext.pushGraphicsLayerScaleInternal`/`popGraphicsLayerScaleInternal` (`UiAnimatedVisibility.kt`'s `withGraphicsLayerScale`), carried on `UiDrawPrimitive.transform` (`UiPrimitiveTransform`) through to a real GPU vertex-shader transform in BOTH backends (`ui_quad.vert`/`ui_glyph.vert`/`ui_texture.vert`/`ui_rounded_quad.vert` for Vulkan, the `.wgsl` siblings for WebGPU) | Faithful (scale only, see `docs/tasks/2026-08-02-graphicslayer-rotation-scale.md`) | Real, GPU-side, not CPU-side geometry mutation -- unlike alpha (a CPU color multiply), scale changes geometry, so `UiDrawPrimitive.Quad`/`RoundedQuad`/`Glyph`/`Texture` each grew an optional `transform: UiPrimitiveTransform?` field threaded from `UiContext`'s emission choke point (`withTransform`, mirroring `scaledByAlpha`'s pattern) through to a new per-vertex `vec4` attribute (`scale.xy` + `pivot.xy`) in every UI vertex shader in both backends -- applied as `pivot + (position - pivot) * scale` before the screen-to-NDC transform. Batching investigation (see the task doc): same-type primitives already batch into one draw call via per-vertex-varying attributes (color already works this way), so scale/pivot rides along as one more per-vertex attribute -- no un-batching or instance-data redesign needed, scaled and unscaled primitives of the same type still coalesce into the same draw call. Verified on real Vulkan/MoltenVK hardware (`RendererHeadlessUiGlyphBaselineTest.headlessUiGlyphRenderAppliesGraphicsLayerScale`) and the CPU snapshot rasterizer (`UiRasterizerTest.quadWithScaleTransformGrowsAroundItsPivot`) independently, since the GLSL and WGSL shader math are hand-written separately and can drift. **Known gaps, deliberately out of scope for this pass**: (1) rotation is not implemented -- only `scaleX`/`scaleY` + pivot, no rotation matrix/trig; (2) the active clip region does NOT transform with scaled content -- clip/scissor rects stay axis-aligned in pre-transform space, so scaled content can visually overflow its own clip rect; (3) `FilledPath`/`StrokedPath`/`GradientQuad` don't carry `transform` (no dedicated shader of their own to extend in this pass) -- only `Quad`/`RoundedQuad`/`Glyph`/`Texture` are GPU-scaled; (4) nested `withGraphicsLayerScale` blocks with different pivots don't compose via real matrix math -- the innermost active transform simply wins. |

## Tally

- **Modifier**: 9 Faithful (`weight()`+`fillMax*` starvation fixed in commit `9455bc51`, moved from Diverges), 4 Diverges (scroll-modifier overwrite, `graphicsLayer` block shape, standalone `alpha()`, `clickable` -- opt-in per-widget resolution rather than automatic on any composable, moved from Not implemented), 0 Not implemented (`pointerInput` folded into the `clickable` row above as a deliberately-skipped escape hatch; standalone rotate/scale/zIndex folded into the `alpha()` row above)
- **Scope/DSL**: 4 Faithful, 3 Diverges (two-pass trial-measure model -- partially optimized in commit `55dd0681` for `Center`/`End`/`SpaceBetween`/`SpaceEvenly`/`SpaceAround` arrangements, still diverges in the general case; the now-fixed-but-noteworthy wrap-height-corruption history; `LazyColumn`/`LazyRow` now real but fixed-item-height/explicit-scroll-state-shaped, moved from Not implemented), 1 Not implemented (`AbsoluteScope` as non-analog)
- **Animation**: 2 Faithful (`animateFloatRepeatable` ergonomics, `Easing`), 5 Diverges (`animateFloat` call shape, `animateFloatTween` call shape, no reusable `AnimationSpec` value type, forced trial-measurement guard, `rememberTransition` scoped-down single-progress-value coordinator vs. Compose's multi-child `updateTransition`) -- `animatedVisibility` (built on real graphicsLayer alpha) is tallied under GraphicsLayer below, not here.
- **GraphicsLayer**: 2 Faithful (real per-primitive alpha compositing, `UiAlphaEffect`/`withGraphicsLayerAlpha`/`animatedVisibility`, alpha-only; real GPU-side scale compositing, `UiScaleEffect`/`withGraphicsLayerScale`/`UiPrimitiveTransform`, scale-only, no rotation, no clip-transform), 1 Diverges (marker-hook block shape vs. Compose's configuration-lambda block)

The `weight()` + `fillMaxWidth()`/`fillMaxHeight()` starvation that used to be the single
most load-bearing "looks safe, isn't" finding here is fixed as of commit `9455bc51` --
mixing `weight()` and `FillMax` siblings in the same `row()`/`column()` now resolves in
Compose's real order (weighted siblings first, `FillMax` leftovers last) instead of
being order-dependent. `graphicsLayer`'s alpha channel is now real too (`UiAlphaEffect`,
applied once at `UiContext`'s primitive-emission choke point, proven end-to-end by
`animatedVisibility` and `UiPopup.kt`'s fade), and as of this pass its scale channel is
real too (`UiScaleEffect`, GPU-applied in both backends' vertex shaders) -- the remaining
load-bearing gap in this section is rotation (still not implemented at all) and clip
staying axis-aligned under an active scale (a deliberate, documented staged-scope gap, see
`docs/tasks/2026-08-02-graphicslayer-rotation-scale.md`), plus the call shape
(`graphicsLayer(effect)`, not a configuration lambda) still diverging from Compose.
