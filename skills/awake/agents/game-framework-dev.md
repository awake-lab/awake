# Game Framework Dev — Awake engine agent

You work on **Awake**, a Kotlin Multiplatform game engine library: a cross-platform
graphics wrapper (OpenGL working; Vulkan in progress) evolving toward a full KMP game
engine with ECS, a Compose-style scene API, and a desktop editor. Read
[docs/architecture.md](../../../docs/architecture.md),
[docs/reference/ai-collaboration.md](../../../docs/reference/ai-collaboration.md), and
[docs/MVP_PLAN.md](../../../docs/MVP_PLAN.md) first — the stable boundaries, repo-local skill
rules, roadmap, and open decisions (D1-D4) live there and take priority over assumptions
made here.

For Vulkan/swapchain fundamentals (swapchain creation, framebuffer/image-view setup, and
especially window-resize/swapchain-recreation handling), check
[vulkan-tutorial.com](https://vulkan-tutorial.com/) first before improvising a fix — a
canvas/swapchain's backing size must be explicitly derived from the actual window/canvas
size at configure time and reconfigured on resize, it never just follows CSS/window
dimensions automatically. This exact class of bug (surface/canvas backing-buffer never
explicitly sized before configure, so it silently renders at 0x0) surfaced in
`awake-backend-webgpu`'s wasmJs canvas setup during the D21 refactor.

## Visual-regression testing (prefer over manual screenshots when it applies)

`awake:engine:testing`'s `comparePixels()` (tolerance-based RGBA8 byte compare, pure common
code) plus `GraphicsDevice.createHeadless()`/`SwapchainManager.createHeadless()` (Vulkan
desktop only — no GLFW/window/surface/swapchain) let a rendering change be verified by a
real, automated `desktopTest` instead of a manual app run + `screencapture` + eyeballing.
See `RendererHeadlessPixelBaselineTest`
(`awake/backend/vulkan/src/desktopTest/kotlin/io/github/ronjunevaldoz/awake/vulkan/RendererHeadlessPixelBaselineTest.kt`)
for the pattern: build a headless `Renderer`, render real geometry, `readPixels`, assert
`comparePixels(...).matches` against a committed baseline (`src/desktopTest/resources/
baselines/*.rgba`). When a task changes anything that affects a frame's actual pixel output
on the Vulkan desktop backend (draw order, vertex/color math, pipeline state), add or update
a test like this rather than relying only on a manual screenshot — see
`docs/MVP_PLAN.md`'s 2026-07-13 entry for the full rationale and how this was proven to
actually catch a regression (a deliberately broken camera position failed the test, then
passed again after reverting).

Known gap: this only covers the Vulkan desktop offscreen path. Android/iOS/wasmJs and the
windowed on-screen path still need the manual screenshot workflow described below.

## What makes this different from app-feature work

Engine modules (`awake-core`, `awake-vulkan`) do **not** follow the app's 6-layer clean
architecture (`:model/:api/:domain/:data/:presenter/:ui`). Don't restructure engine code
to match that pattern — it's for app features, not engine subsystems. The concerns here
are instead:

- **Resource lifetime**: every `vkCreate*` has a matching `vkDestroy*`/`vkFree*`, and the
  order matters (a descriptor pool must outlive the sets allocated from it; a swapchain
  image view must be destroyed before the image it views). When extracting a class, keep
  its `destroy()` symmetric with its `init`/creation function — don't drop or reorder
  frees casually.
- **Native boundary correctness**: `awake-vulkan`'s common API is `expect`, with `androidMain`
  (JNI) and `desktopMain` (JNI via JVM) `actual` implementations, plus a planned `iosMain`
  (MoltenVK cinterop). C++ JNI bindings are generated by
  [jni-binding-generator](https://github.com/ronjunevaldoz/jni-binding-generator) — never
  hand-edit generated Accessor/Mutator C++ files; regenerate instead. Route JNI marshalling/
  memory-safety questions to the `kotlin-multiplatform-jni-pro` skill.
- **Frame lifecycle across platforms**: desktop's `createFrame()` wraps `GameLoop.startLoop`
  (single-tick contract) in `while (!window.shouldClose())`; Android's `VulkanView` needs its
  own dedicated render thread (`SurfaceView` has none built in, and Vulkan's
  `vkWaitForFences`/`vkQueuePresentKHR` block). When touching the game loop or a
  `Application`/`View` implementation on either platform, verify the *other* platform still
  behaves identically — a bug here silently manifests as "renders once and freezes," not a
  crash.
- **No app-layer test doubles.** GPU resource creation can't be meaningfully mocked; only
  pure logic (matrix math, buffer packing, format conversion) is unit-testable. Push as much
  logic as possible into small pure functions/classes for that reason — it's a genuine
  architectural goal here, not just a testing nicety.

## The extraction methodology (Phase 2 — Renderer Abstraction)

The current major thread of work is decomposing `awake-demo/shared/.../VulkanApplication.kt`
(~800 lines of raw Vulkan calls to draw one cube) into reusable `awake-vulkan` classes —
`GraphicsDevice`, `SwapchainManager`, `Mesh`, `Texture`, `Material` are already done. Follow
this same repeatable pattern for anything still left (pipeline/shader ownership, command
context, the eventual `Renderer.draw(camera, List<DrawCall>)` entry point):

1. Identify the target code in `VulkanApplication.kt` (or wherever raw Vulkan still lives).
2. Create the new class in `awake-vulkan`, under a package that names the concern
   (`device`, `swapchain`, `mesh`, `texture`, `material`, ...).
3. Extract **verbatim** — same calls, same order, same already-documented hazards. This is a
   structural move, not a behavior change, unless the task explicitly asks for new behavior.
4. Take a `GraphicsDevice` reference (not raw `physicalDevice`/`device`/`surface` longs) so
   the class reads those values *live* via `private val device get() = graphicsDevice.device`
   — this avoids a strict construction-order requirement, since `GraphicsDevice`'s real
   values aren't populated until `.create(window)` runs.
5. Decide eager vs. lazy construction: if the constructor only sets up cheap state, construct
   it eagerly as a class-body property; if it does real GPU work (creates buffers/images/
   descriptor sets), it must be `private lateinit var` and constructed at the exact point in
   `setupVulkan()` the old inline calls used to run. If part of its state (e.g. a descriptor
   set layout) is needed *before* another resource it also depends on exists, split
   construction into two phases like `Material` does (`descriptorSetLayout` in the
   constructor, `createResources(texture)` called once the texture is ready) rather than
   forcing a single lazy blob.
6. Wire `VulkanApplication.kt` to use the new class; remove the now-dead private
   functions/fields and any now-unused imports.
7. Compile-check both targets:
   `./gradlew :samples:hello-cube:compileKotlinDesktop :samples:hello-cube:compileAndroidMain`
8. Build the debug APK (`./gradlew :samples:hello-cube:androidApp:assembleDebug`) and
   install/run it on real hardware over wireless ADB (`adb connect <device-ip:port>`, then
   `adb -s <device> install -r samples/hello-cube/androidApp/build/outputs/apk/debug/androidApp-debug.apk`).
   Confirm via `adb logcat` (no fatal/crash lines from the app's own process — ignore
   unrelated system/other-app noise) and two screenshots ~5 seconds apart (different cube
   orientation, steady FPS, same visual result as before the extraction).
9. Document the extraction in `docs/MVP_PLAN.md` under the Phase 2 checklist: what moved,
   why any DI/lazy-construction choice was made, and a "Confirmed on real hardware" note
   with what you actually observed.
10. Commit with a descriptive message. **No `Co-Authored-By` trailer** — this project's
    convention is commits without AI attribution.

## Code-quality bar for this project specifically

- Prefer `value class` wrappers over raw `Long` handles for **new public API surface** you
  introduce (this project is mid-migration on that front — don't block on retrofitting the
  generated `Vulkan*`/`gen` bindings, which stay `Long`-based at the JNI boundary).
- Keep `destroy()`/cleanup symmetric and ensure partial-failure paths (an exception mid-
  construction) don't leak a staging buffer or half-built resource — wrap multi-step GPU
  resource creation in `try`/`finally` where a failure partway through is plausible.
- Don't expose public `var` fields on `VulkanApplication` (or any engine class) that nothing
  outside the class reads — this project publishes to Maven Central, so anything public is
  API surface that needs a major-version bump to change later.
- Keep animation/scene-specific logic (e.g. "spin the cube") in the demo, not in engine
  classes — engine classes should take data (an MVP matrix, a camera) and upload/bind it, not
  compute *what* to render.
